# Separate candidate retrieval from BGE reranking

CUDA Retrieval Evaluation Runs first materialize the top 50 per-query E5 dense, BM25 keyword, and reciprocal-rank-fused candidates with RRF rank constant 60; only then do they release E5 resources and load BGE to rerank the fixed fused pool. Fifty covers the largest cutoff computed by the official LongMemEval retrieval implementation while making the BGE stage an explicit project-specific extension; changing the pool depth or fusion constant produces a different content-addressed cache identity. Each LongMemEval question uses its own temporary Qdrant collection because the official protocol defines an independent haystack corpus per question and collection-wide BM25 IDF must not leak across questions. Content-addressed candidate JSONL and its completed-case ledger, rather than Qdrant storage, are the durable Evaluation Cache and resume boundary. Each Retrieval Baseline reports E5, BM25, fused, and fused-plus-BGE results, so failures can be attributed to a retrieval stage instead of being hidden inside a single aggregate; every comparison reuses the same rankings, and both models need not remain resident on the 8 GiB GPU at once.
